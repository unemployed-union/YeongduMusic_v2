## 구현 내용과 경계

NAS 후보의 후속 실기기 검증은 [NAS 페이지·캐시 검증](nas-page-verification.md)에 정리했다. 현재 서버에서 큰 페이지와 병렬 요청이 동작함을 확인했으며, 확대 적용에는 기존 100곡 캐시의 호환 처리가 필요하다.

- `src/features/library/song-library.ts`: 원본 Query 페이지를 WeakMap 키로 삼아 **페이지당 직전 가공 결과 하나**를 보관한다. 서로 다른 화면이 만든 libraries/edits 객체라도 실제 곡 배열·수정 맵이 같으면 재사용한다. 소스 순서, 계정 키, 병합 모드, NAS 포함 여부, 메타데이터/아트 수정 맵, 수정 범위·기본 URI, stale 값은 모두 비교한다. 다른 입력이 오면 항목을 교체하며 변경 이력을 누적하지 않는다.
- `src/features/library/queries.ts`, `use-source-libraries.ts`: 기존 조회·구독·취소·재시도 경로를 그대로 두고 공통 가공을 연결했다. 계정 범위와 세대 변경도 가공 입력에 반영한다. NAS 실패 시 로컬 fallback과 실패 안내를 유지하며 부분 데이터를 성공한 NAS Query로 기록하지 않는다. fallback의 임시 빈 페이지는 전역으로 보관하지 않는다.
- `src/features/hidden-music/rules.ts`: 가공된 페이지와 숨김 프리셋 참조가 같으면 같은 필터 결과를 반환한다. 프리셋 교체 시 다시 필터링한다. 공통 결과 소비자가 배열을 직접 정렬/수정하는 경로는 발견되지 않았고, 화면 정렬은 기존처럼 복사본에서 수행한다.
- 앨범/아티스트 그룹 설정은 공통 곡 데이터와 독립적이다. 기존 selector 의존성과 QueryObserver 메모를 유지해 설정 변경 시 파생 결과를 갱신한다. 상세 화면의 곡 선택·트랙 정렬도 기존 경로를 유지했다. 별도의 전역 앨범/아티스트 상세 인덱스는 추가하지 않았다. 여러 source override가 번갈아 같은 원본 페이지를 사용하면 직전 항목이 교체되어 재계산될 수 있다.
- `src/services/local-music/storage.ts`: `readLocalSong(id)`와 전체 읽기가 같은 `decodeLocalSong`을 사용한다. 파일명·필드·원본 폴더 검증, 복구 저널 처리, `albumSource` 기본값을 공유한다. 단건 조회는 DB 키와 JSON의 ID 일치도 복구 전에 확인한다. 태그 파일 교체·다운로드 중복 확인·삭제에 연결했으며 기존 mutationQueue를 유지했다. 단건 작업은 무관한 다른 곡의 손상 때문에 실패하지 않지만, 전체 읽기는 여전히 전체 손상을 검출한다.
- 로컬 작업 후 store/UI의 전체 갱신은 보존했다. 따라서 단건 작업 전체가 항상 DB 한 행만 읽게 되었다는 의미는 아니다. 기존 길이 저장의 단건 SQL 경로도 유지했다.
- `src/services/playback/persistence.ts`: 동기 변경 묶음의 마지막 상태만 변환·직렬화하고 기존 writeTail로 순서대로 쓴다. recorder 종료 시 아직 예약된 상태를 즉시 캡처해 마지막 선택이 누락되지 않도록 했다. 저장 실패 후 다음 저장, clear 뒤 이전 큐가 다시 저장되지 않는 동작을 검증했다. 서로 다른 실행 흐름의 변경은 각각 저장하며, 매 저장 시 전체 v1 큐 직렬화는 여전히 수행한다.
- `src/features/playlists/song-picker.tsx`, `src/stores/playlists.ts`: 선택 가능 곡 계산은 라이브러리·선택 집합·기존 곡 집합이 바뀔 때만 실행한다. 선택 순서가 아니라 라이브러리 순서대로 추가하는 규칙을 보존했다. 순서 변경은 보이는 ID 집합으로 필터링하되 원래 preset 순서를 기준으로 이웃 곡을 교환해 숨김/누락 곡의 자리를 보존한다.

새 의존성, 저장 스키마, Provider 계약, 앱 식별자, 재생 엔진 및 UI 디자인 변경은 없다. WeakMap 가공 결과와 필터 배열에 추가 메모리가 필요하지만 이전 페이지 수명에 연결되며 영구 저장하지 않는다. 실제 힙 사용량은 측정하지 않았다.

모든 시나리오에서 값과 순서를 함께 확인했다. 위 수치를 앱 시작 시간·전체 수정/삭제 작업·실제 재생 제어 응답 시간 개선율로 해석해서는 안 된다. NAS 요청 횟수는 이번 작업으로 줄지 않았다.

- `scripts/check-file-metadata.cjs` 보강: 실제 복구 구현을 사용해 전체 읽기와 단건 읽기 모두 파일 교체 중단 후 저널·백업 복구를 검증했다.
- 전체 실행 가능한 `.cjs` 검사 **80개 통과**, 타입 검사·ESLint 통과. 기존 취소·오프라인·백업·인증·재생 복원·탐색·셔플/반복·백그라운드 저장 검사 포함.
- Android arm64 Release APK 생성 성공. iOS Hermes 번들 생성 성공. Windows이므로 iOS Swift/Xcode 빌드와 iOS 잠금 화면 네이티브 검사는 미실행이다.

## 남은 확인

1. 실서버에서 NAS 페이지별 RTT·허용 limit·안정된 정렬을 확인한 뒤 페이지 확대와 작은 동시 요청 수를 비교한다. 실패·401·취소·조회 중 삽입/삭제·기존 100곡 캐시를 함께 검증해야 한다. 점진 표시는 아직 도입하지 않았다.
2. Android/iOS Release 기기에서 같은 대형 라이브러리로 첫 표시·탭 전환·검색·곡 수정·순서 변경을 비교하고 공통 결과 보관의 힙 비용을 확인한다.
3. 재생/일시정지·셔플·반복을 연속 조작한 직후 background/강제 종료하고 기존 큐·선택·설정이 재시작 후 복원되는지 확인한다. 재시작은 기존처럼 곡 처음부터 일시정지 상태로 복원해야 한다. 비동기 저장이 끝나기 전 프로세스가 강제로 종료되는 경우의 내구성을 이번 mock 검사로 보장하지 않는다.
4. 다른 앨범/아티스트를 연속으로 여는 구간이 실제 기기에서 여전히 병목이면 상세 결과/인덱스 공유를 후속 검토한다. 현재는 기존 observer 캐시와 공통 곡 가공 공유까지만 적용했다.

구현 시 공식 [SDK 58](https://docs.expo.dev/versions/v58.0.0/), [SQLite 단건 조회 API](https://docs.expo.dev/versions/v58.0.0/sdk/sqlite/)를 확인했다.
