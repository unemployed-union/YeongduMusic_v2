# NAS 페이지 확대·병렬 조회·캐시 호환 검증

## 결론

현재 연결된 NAS와 계정에서는 **500곡 페이지 및 동시 요청 2개를 사용할 수 있다.** 전체 1,546곡의 수·중복·순서가 기존 100곡 순차 결과와 일치했다. 1,000곡 요청도 첫 페이지에서 정상 응답했지만, 전체 목록 비교는 500곡 방식으로 수행했다. 다른 NAS의 최대 limit이나 모든 서버 버전의 지원 범위를 보장하는 결과는 아니다.

**요청 limit만 바꾸는 것은 오프라인 호환이 되지 않는다.** 현재 캐시 조회는 offset·limit가 정확히 같은 키만 읽는다. 기존 100곡 캐시를 새 요청 크기에 맞춰 조합하거나, 캐시의 100곡 저장 단위를 유지하는 호환 처리를 먼저 구현해야 한다. 이번 작업은 검증 범위이며 앱의 조회 크기·동시성·캐시 구현을 변경하지 않았다.

## 실행 조건

- 연결된 삼성 SM-S948N, Android API 37에서 현재 앱에 저장된 HTTPS NAS 주소와 세션 사용.
- `SYNO.AudioStation.Song.list`, API v3, `library=all`, `additional=song_tag,song_audio`. discovery 결과 지원 버전은 v1~v3.
- 설치된 Release 앱과 같은 서명의 별도 진단 APK를 이용했다. SecureStore 세션은 기기 내부에서만 읽어 사용했고, PC로 내보내거나 로그에 기록하지 않았다.
- 일반 instrumentation 재시작 모드에서는 DNS 조회가 실패했다. 앱에서는 정상 연결된다는 사용자 확인 후 `am instrument --no-restart`로 앱 실행을 유지하자 조회가 성공했다. 초기 실패의 원인은 확정하지 않았으며 NAS의 지원 문제로 해석하지 않았다.
- 진단 요청은 API discovery와 곡 목록 읽기뿐이다. 앱 SQLite는 `OPEN_READONLY`로 열었으며 앱의 로그인·설정·음악·캐시를 진단 코드에서 쓰거나 삭제하지 않았다. 테스트 후 별도 진단 APK를 제거했다.

## 실서버 응답과 성능

| 단일 요청 limit | 실제 곡 수 | song_tag 존재 | song_audio 존재 |
| --- | --- | --- | --- |
| 100 | 100 | 100 | 100 |
| 250 | 250 | 250 | 250 |
| 500 | 500 | 500 | 500 |
| 1,000 | 1,000 | 1,000 | 1,000 |

전체 목록을 각 방식으로 3회 읽었다. 순서는 첫 회 100 순차 → 500 순차 → 500 병렬, 다음 회에는 반대로 배치해 편향을 줄였다.

| 전체 1,546곡 조회 | 요청 수 | 중앙값 | 최소~최대 |
| --- | --- | --- | --- |
| 100곡, 순차 | 16 | 13.02초 | 10.43~14.46초 |
| 500곡, 순차 | 4 | 4.08초 | 3.17~4.39초 |
| 500곡, 동시 요청 2개 | 4 | 2.58초 | 2.45~5.08초 |

9회 모두 total=1,546, 수신 1,546, 고유 ID 1,546이었고 첫 100곡 순차 조회와 ID 순서가 같았다. 병렬 응답은 완료 순서가 아니라 offset 순서로 합쳤다. 전체 스캔 중 각 페이지의 total이 기준 total과 같은지도 확인했다. 메타데이터 필드 존재는 위 단일 페이지에서 확인했으며 전체 메타데이터 값의 바이트 단위 동일성을 비교한 것은 아니다.

측정에는 기기에서의 HTTP 요청·응답 수신·Java JSON 파싱·ID 수집이 포함된다. React Native fetch, SQLite 쓰기, JS 곡 변환·필터·그룹화와 화면 렌더 시간을 포함한 앱 전체 로딩 측정은 아니다. 병렬 방식의 마지막 회는 순차 방식보다 느렸으며, 3회 표본만으로 항상 일정한 개선율을 보장할 수 없다.

## 실제 기기 캐시 확인

현재 계정과 `library=all/provider-v1` 범위에서 확인했다.

- 100곡 페이지 16개, 총 1,546곡, 고유 ID 1,546개.
- 각 offset과 페이지 total·길이가 연속적이고 마지막 페이지까지 완전했다.
- 캐시 ID 순서와 실서버 100곡 순차 결과가 일치했다.
- `offset=0, limit=100` 키는 존재했지만, `limit=500/1000` 키는 없었다.
- 완전한 기존 100곡 페이지들은 500곡 단위로 재구성할 수 있는 데이터 상태였다. 현재 앱이 자동으로 그렇게 조합하는 것은 아니다.

실제 앱 캐시·repository 코드를 Node SQLite 메모리 DB에 연결한 별도 검증도 수행했다.

1. 기존 100곡 키 16개를 만든 뒤 네트워크 실패를 모의하면 100곡 요청은 `stale=true`로 복구된다.
2. 같은 상태의 500/1,000곡 요청은 기존 100곡 키를 자동으로 읽지 못하고 실패한다.
3. 연속된 100곡 페이지 다섯 개의 total·길이를 확인하고 합치면 첫 500곡의 순서가 맞는다.
4. 500곡 키를 추가해도 기존 100곡 키와 공존한다.
5. 다른 계정 키는 읽히지 않고, 취소된 요청은 캐시 조회 전에 중단된다. 직렬화된 데이터에 아트 URL의 인증 정보가 포함되지 않는다.

이 검증은 DB 구조를 바꾸거나 기기의 네트워크를 끄지 않고 수행했다. 실제 비행기 모드나 통신 끊김 상태의 앱 UI를 확인한 것은 아니다.

## 적용 시 권장 경로

1. **500곡 순차부터 적용:** 요청 수 감소 효과가 크고, 병렬화보다 기존 취소·오류 흐름을 보존하기 쉽다.
2. **100곡 캐시 호환을 함께 구현:** 큰 응답을 기존 100곡 단위로 저장하고, 큰 요청의 오프라인 fallback은 연속된 기존 페이지로 구성하는 방식이 적합하다. 모든 조각의 total·offset·길이와 계정 범위를 검증하고, 일부가 없거나 불일치하면 성공한 전체 결과로 내보내지 않아야 한다. 조각 저장의 중간 실패도 검증해야 한다.
3. **병렬화는 최대 2개로 제한:** 첫 응답으로 총수·실제 반환 크기를 확인한 뒤 요청하고, offset 순서로 합치며 total 변경·중복 ID·누락·취소·계정 교체를 검증한다.
4. 서버가 큰 페이지를 거절하거나 일부 응답만 주는 경우 기존 100곡 경로로 돌아갈 정책이 필요하다. 인증 만료와 취소를 일반 네트워크 fallback으로 숨기지 않아야 한다.

현재까지 읽기 검사 중 서버 곡 추가/삭제는 수행하지 않았다. 목록 변경 중의 일관성, 401/권한 만료, 느린 응답·요청 취소 및 부분 캐시 저장은 확대 구현의 회귀 검증 항목으로 남는다.

## 산출물과 검사

- `dist/nas-verification/results.json`: 실기기 원시 측정값과 집계.
- `device-benchmark.log`: 인증 정보·곡 ID·곡 제목·서버 주소를 제외한 기기 결과.
- `cache-probe.cjs`, `cache-compatibility.log`: 실제 앱 코드와 SQLite 메모리 DB를 사용한 호환성 검사.
- `probe/`: 앱과 분리한 읽기 전용 진단 소스. 임시 소스와 산출물은 Git에 포함하지 않는다.
- 타입 검사·ESLint 및 기존 NAS 관련 회귀 5개(`check-library-state`, `check-album-library`, `check-auth-session`, `check-http-requests`, `check-music-providers`) 통과.

진단 실행기는 [Android instrumentation](https://developer.android.com/guide/topics/manifest/instrumentation-element)과 설치된 Expo SecureStore/SQLite 구현을 기준으로 작성했다. 앱 코드는 현재 100곡 순차 조회를 유지한다.
